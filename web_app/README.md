# Class Diagram

A web application generated by [BESSER](https://github.com/BESSER-PEARL/BESSER):
a FastAPI backend (`backend/`) and a React + Vite frontend (`frontend/`).

## Run it

```bash
docker compose up --build
```

| | |
| --- | --- |
| Web app | http://localhost:3000 |
| API | http://localhost:8000 |
| API docs | http://localhost:8000/docs |

## Run it without Docker

Backend (Python 3.11 or later), on port 8000:

```bash
cd backend
pip install -r requirements.txt
python main_api.py
```

Frontend (Node.js 20 or later), on port 3000:

```bash
cd frontend
npm install
npm run dev
```

## Data

The backend stores its data in a SQLite file under `backend/data/` (the
`sqlite_data` volume with Docker Compose). Set `DATABASE_URL` to use another
database.

## Pointing the frontend at another backend

The frontend reads the API address from `VITE_API_URL` and falls back to
`http://localhost:8000`:

```bash
cd frontend
VITE_API_URL=http://localhost:8080 npm run dev
```

Vite reads `VITE_*` variables at build time, so a production image takes the
address as a build argument: `docker-compose.yml` passes it that way.

## Method endpoints (modeled behavior)

Every method is a `POST` that takes `{"params": {...}}` (an empty `{}` body is
fine for parameterless methods) and returns the updated/created record, shaped
exactly like the entity's GET routes. A guard violation answers 409, a missing
or malformed parameter 422, an unknown id 404 — never a fake success.

| Method endpoint | Params | Effect | Guards |
| --- | --- | --- | --- |
| `POST /resolution/{id}/methods/activate/` | none | `status` → `ACTIVE`, `updatedAt` = now | 409 if already `ACTIVE` |
| `POST /resolution/{id}/methods/pause/` | none | `status` → `PAUSED`, `updatedAt` = now | 409 if already `PAUSED` |
| `POST /resolution/{id}/methods/complete/` | none | `status` → `COMPLETED`, `updatedAt` = now | 409 if already `COMPLETED` |
| `POST /habit/{id}/methods/markDone/` | `doneAt` (ISO datetime) | `lastDoneAt` = `doneAt`, `currentStreak` + 1 | 409 if `doneAt` < current `lastDoneAt`; 422 if `doneAt` missing/malformed |
| `POST /habit/{id}/methods/resetStreak/` | none | `currentStreak` → 0 (`lastDoneAt` kept) | — |
| `POST /progressentry/{id}/methods/edit/` | `notes` (str) and/or `amount` (float), `null` clears | updates `notes`/`amount` | 422 if neither key present |
| `POST /progressentry/{id}/methods/remove/` | none | deletes the entry | — |
| `POST /subgoal/{id}/methods/markComplete/` | none | `completed` → `true` | 409 if already completed |
| `POST /user/{id}/methods/createResolution/` | `title` (str, required), `description` (str, optional) | creates a `Resolution` owned by the user with `status` = `PLANNED` | 422 if `title` missing |
| `POST /user/{id}/methods/addProgressEntry/` | `resolution` (id), `entry` (`{date, notes?, amount?, habit?}`) | creates a `ProgressEntry` authored by the user, linked to the resolution (and habit, if given) | 400 if the resolution/habit is not the user's own or does not exist |

Example — mark a habit done and see the streak move:

```bash
curl -X POST http://localhost:8000/habit/1/methods/markDone/ \
  -H "Content-Type: application/json" \
  -d '{"params": {"doneAt": "2025-01-15T08:30:00"}}'
# -> {"habit": {..., "currentStreak": 1, "lastDoneAt": "2025-01-15T08:30:00"}, "progressEntries_ids": [...]}
```

The same behavior is documented on the ORM methods in
`backend/sql_alchemy.py` (`Resolution.activate/complete/pause`,
`Habit.markDone/resetStreak`, `ProgressEntry.edit/remove`,
`SubGoal.markComplete`, `User.addProgressEntry/createResolution`), which the
handlers above call before persisting.
